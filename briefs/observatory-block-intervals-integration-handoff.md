## Runtime clarification: applied-head invalidation

Root decision, 15 October 2026, after rereading `NetworkMonitor.deriveHead` and `recordProvenProgress` at the isolated development baseline. This interprets the accepted FR-021/C-8 proof requirement; it does not change monitor consensus semantics or add a health classifier.

For metric invalidation, use accepted, validated **applied** contexts from the same configured RPC source and chain. A lower applied level proves rollback; a different applied hash at the same level proves local branch replacement, including when the navigator's existing progression classification is `same-level-round`. Two adjacent applied levels with a supplied, proven successor predecessor unequal to the previous applied hash establish a continuity contradiction. These fence the metric generation and stale retained facts under the existing contract.

A progression label alone is insufficient when the underlying proof is missing. A forward gap with unknown ancestry, normal protocol transition, same-network RPC source rotation, or a lower height reported by another provider does not prove reorganization. Proposals, votes, selected candidates and estimated rounds alone are not applied contexts. Material accepted applied changes may still qualify as refresh triggers subject to the existing start spacing; trigger eligibility and invalidation are distinct decisions. Record positive and negative classification cases in the implementation handoff and production tests.
